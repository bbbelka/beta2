# MAISON D’ANTIQUE — каталог и заявки на приобретение

Сайт размещается как статический проект; каталог, аккаунты, заявки и переписка используют Supabase. Заявка не является оплатой или подтверждённой покупкой: наличие и условия приобретения менеджер согласует с покупателем в чате.

## Заявка на приобретение

- Корзина хранится по существующей клиентской логике и показывает актуальные карточки каталога.
- Для отправки заявки пользователь входит в аккаунт. Клиент передаёт серверной RPC только ID товаров и количество; цены и доступность повторно проверяются на сервере.
- RPC `public.create_purchase_request(jsonb, uuid)` сохраняет снимок названий, фотографий, ссылок и цен в `orders`, формирует номер `MDA-YYYY-NNNNNN`, связывает заявку с существующим диалогом покупателя и добавляет одно системное сообщение.
- Повтор с тем же ключом идемпотентности и составом возвращает сохранённую заявку. Состав заявки не подменяется актуальными данными каталога.
- Корзина очищается только после подтверждения сохранённой заявки. При ошибке она сохраняется для повторной попытки.
- Пользователь видит только свои заявки; администратор — заявки в пределах действующих RLS-политик. Обычный клиент не может напрямую создавать/изменять записи `orders` или отправлять системные сообщения чата.
- Наличие проверяется по `products.available`; `stock_quantity` и списание остатков в новом потоке не используются.

## Миграция

`purchase-request-migration.sql` — локальный SQL-файл для ручной проверки и применения. Он не запускался из сайта и не применялся к Supabase в этой рабочей копии.

Миграция предполагает, что уже существуют:

1. `products`, `orders`, `profiles`, `public.is_admin()` из `supabase-schema.sql`;
2. необходимые поля профиля из `profile-migration.sql`;
3. `conversations`, `messages` и связанные RLS-политики из `messages-migration.sql`;
4. при использовании архива чатов — `chat-archive-migration.sql`;
5. старые функции администрирования заказов из `inventory-migration.sql`, если их использует текущая рабочая база.

Для нового проекта предварительно проверьте и примените базовые файлы именно в этом порядке; затем вручную рассматривается `purchase-request-migration.sql`. Для уже настроенного проекта сначала проверьте фактическую схему и применённые миграции: не запускайте повторно базовые SQL-файлы вслепую. Новая миграция не требует `inventory-migration.sql` или `availability-only-order-migration.sql` для оформления заявок. Не применяйте её к рабочей базе без резервной копии и проверки в целевом проекте.

Исторические `orders`, `order_items`, RPC оформления и связанные данные не удаляются. Пользовательский клиент не вызывает `create_shop_order`; legacy-данные отображаются отдельно от заявок по наличию `request_number`.

## Кабинет и управление магазином

- В личном кабинете раздел «Мои заказы» показывает снимки заявок и старые заказы. Для заявки доступно действие «Обсудить заявку».
- Панель владельца доступна только аккаунтам с ролью `admin` и показывает состав заявок, покупателя и переход к диалогу.
- Администратор вручную управляет товарами. Наличие определяется только `products.available`; недоступный предмет нельзя добавить в корзину.
- Фотографии товаров хранятся в Supabase Storage в `product-photos`; в существующей конфигурации лимит — 8 МБ и разрешены JPEG, PNG, WebP, GIF и AVIF.
- Встроенный чат сохраняет обычные сообщения и вложения; системное сообщение заявки связано с записью заявки, чтобы его нельзя было подделать клиентским вызовом.

## Проверки и ограничения

Локальные тесты: `node --test tests/*.test.cjs`. Они проверяют клиентский контракт, повторы, миграцию и статические свойства интерфейсов, но не создают заказ в настоящей Supabase и не доказывают работу её RLS. После ручного применения миграции необходимо отдельно проверить оформление под тестовым пользователем, доступ менеджера, отсутствие доступа к чужим заявкам/чатам и повтор запроса с тем же ключом.

Не добавляйте `service_role` key в `js/config.js` или другие публичные файлы. Браузер использует только публичный ключ Supabase; доступ к данным обеспечивается серверной RPC и RLS.

Клиент Supabase закреплён за версией с SHA-384 SRI. Модуль удаления фона загружается по запросу и проверяется по SHA-384; WASM и модель IMG.LY остаются на версионном CDN и отдельно не проверяются по хешу. Это остаётся риском цепочки поставки.
